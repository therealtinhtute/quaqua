# W2 pipeline — resumable Fail + single build gate (design)

Read at 48fcef2 (`quaqua/sude-w2pipe` = this worktree HEAD). Design only: no edits, no commits, no tests run (none needed to settle the design).

## Decision (finding 1)

**Chosen: recoverable stops become a `PauseForApproval` "blocked gate" inside `PipelineWorkflow`; `Fail` is kept for real terminals only. Engine/runner production code: unchanged.**

`--resume` resolves the gate with `ApprovalResolved { approved: true, reason: Some(<ResumeDirective JSON>) }`; the step then re-enters the failed phase by restarting the same child (same id, new attempt) or, for exhausted rounds, applies the new `max_rounds`. Every decision stays in the journal, so replay is deterministic.

Why this one:
- The W0 contract (`quaqua-rs-split.md` L112, `engine/workflow.rs:145-180`) already has the "suspend for the operator" primitive: `PauseForApproval` → `RunnerOutcome::Blocked` → resume event. It has no resumable-failed state, and `Fail` docs say "Terminate" (`workflow.rs:176`). The runner treats `workflow_failed` as terminal on purpose (`runner.rs:342-356`, its "Finding 4" test `test_resume_after_completed_returns_completed_not_blocked`). The step is wrong to use `Fail`; the runner is right.
- Only the pipeline journals workflows in prod (`SqliteJournal::open` only at `pipeline/mod.rs:719`). Taskforce and `worker prompt` run in memory, so they can't hit this trap. The engine stays as it is.

### Rejected
| Option | Why rejected |
|---|---|
| (b) Reset/truncate the parent's failed journal on `--resume` | The `Journal` trait is append-only (`journal.rs:96-109`, no delete). Deleting only `workflow_failed` is not enough anyway: the report content is in the journal as `activity_completed`, so replay re-reaches the same `Fail`. To work, the reset has to rewrite history back to before the read, which breaks event sourcing. |
| (a′) Engine-level: `workflow_failed` stops being terminal when a new `workflow_resumed` event follows | Changes the frozen W0 API (new `WorkflowEvent`, runner terminal-scan semantics), which needs anh iu's `engine/` gate. `Fail` would then mean two things, and `PauseForApproval` already does this job. |
| (c) Fresh parent workflow id per resume (`pipeline:<task>:genN`), seeded from the state file | Drops history and goes through the lossy seed path (`mod.rs:202-233`, finding 7). Two sources of truth come back (finding 6). |
| (a) as the reviewer phrased it ("non-terminal Blocked awaiting a new child/round") | Kept in substance. The concrete form is the gate above, with no new engine state. |

## Contract change (types / events)

All in `pipeline/` (`engine/` untouched):
1. **`pipeline/state.rs` `PipelineWorkflowState`** (+ `PipelinePhase`, `state.rs:131-140`): add `PipelinePhase::Blocked` and the fields `blocked_from: Option<PipelinePhase>`, `blocked_kind: Option<BlockedKind>` (`Restart | RoundsExhausted`) and `blocked_code: i32`. Keep `Failed` for the terminal ones.
2. **Blocked gate decision**: one helper `fn block(state, from, kind, code, reason) -> StepDecision` returns `PauseForApproval { reason: format!("blocked {code}: {reason}") }`. The driver parses it with `parse_blocked_gate(&str) -> Option<(i32, String)>` (the runner wraps it as `"pause_for_approval: blocked …"`, `runner.rs:806-808`).
3. **`ResumeDirective { max_rounds: u32 }`** (serde, `state.rs`): the driver passes it as the `ApprovalResolved.reason` JSON on every blocked-gate resume, with the current `state.rounds`. On resolve the step sets `state.input.max_rounds = max(old, directive)`. The new limit arrives as a journaled **event**. It must never come through the replay input.
4. **Step `ApprovalResolved`** (`mod.rs:2047-2067`): branch on `state.phase`:
   - `PlanReadyGate`: unchanged.
   - `Blocked` + `approved=false` → `Fail` (terminal operator abort).
   - `Blocked/RoundsExhausted`: apply the directive; `round < max_rounds` → `Fix` + `build_fix_child` (the normal path), otherwise → the same gate again (a new pause, so the exit stays blocked).
   - `Blocked/Restart` → `phase = blocked_from`, rebuild that phase's child (same `child_id`, same round), `StartChild`. The runner already re-dispatches a repeated id (per-id counts, `runner.rs:433-434, 505-519`).
5. **Pin the replay input** (`--rounds` vs snapshot): on the first run (`mod.rs:787`), the driver appends a seq-0 snapshot of the initial state before `run_until_blocked`. Every resume then replays from the journaled `PipelineInput`. A periodic snapshot pinning the old input becomes *correct*: the input is history, and the raised rounds come in through point 3. Without this, replaying with a raised `max_rounds` diverges at the exhaustion step (`mod.rs:1949`): history holds a pause, replay emits `StartChild`. `--resume --rounds` only raises (`mod.rs:409-411`), so earlier rounds can't diverge, but the exhaustion round always does.
6. **Driver resume** (`mod.rs:812-840`): `is_plan_gate` = count(`pause_for_approval`) > count(`approval_resolved`), plus the latest pause reason **not** `blocked `. The current `.any()` pair is wrong once there are 2 or more pauses. A blocked gate gets the directive. `RunnerOutcome::Blocked("pause_for_approval: blocked N: …")` → `finish(blocked, N, reason)`, keeping `N=0` for exhausted rounds (current mapping, `mod.rs:862-866`). It must not go down the pending-child path.
7. **Driver child attempts** (`mod.rs:908-947, 1180`): find the pending child by counts (`child_started` per id > `child_completed|child_failed` per id), from the *latest* `child_started` input. Name the child journal `pipeline:<task>:<child_id>` for attempt 1 and `…#<k>` for attempt k ≥ 2, with k = the `child_started` count for that id. This keeps the child id, so phase classification (finding 4, a separate fix) doesn't change. A restart attempt never re-prompts: set `state.prompted = 1`. It re-validates the report on disk (`already_delivered`, `mod.rs:1227-1243`) or waits on a fresh watchdog.
8. **Child-level trap (same class, `SingleWorkerWorkflow`)**: a child journal ending `workflow_completed{exit≠0}` with no valid report replays terminal on resume (`mod.rs:1188-1196` takes only exit 0, then the `else` at `1365-1395` resumes the terminal child → `exit 4` instantly, forever). Fix: when the latest child journal is terminal with exit≠0, open the next `#k` child journal and wait again (no re-prompt). That is the `worker prompt --resume` semantics from before the cutover.

## Gate 2 (finding 2): one decision

- **Chosen:** one pure fn `decide_build_gate(&BuildFacts) -> BuildGate { Blocked(msg) | NoChanges | Skip(reason) | Review }` in `pipeline/` (no I/O). `BuildFacts = { head, base_sha, declared_no_changes, strategy, changed_lines, top_dirs, review_lines }`. The driver gathers the facts (git + report, `mod.rs:1499-1605`), calls the fn once, writes the pfile line for that variant, and sends `child_output.gate = "no_changes"|"skip"|"review"`.
- The engine Build handler (`mod.rs:2208-2232`) maps `gate`. It **drops** its own `report_has_outcome_no_changes` and `ReviewStrategy::Skip` checks. A missing `gate` (old journals) falls back to `skip_review` (true→skip, false→review) and never infers no-changes from the report.
- `NoChanges` only when `head == base_sha && declared_no_changes`. `head != base` + declaration → `Review`/`Skip` by strategy. `head == base` and no declaration → `Blocked` (today's message, exit 3; it is already resumable, because the child journal is exit 0 and the gate re-runs).
- Restore the aa056d6 pfile line on `NoChanges`: `- build: no commits — builder declared 'Outcome: no changes'; nothing to review`.
- Rejected: the gate in the engine step (needs git facts the pure step can't fetch, so it would mean new activities and more scope); keeping both copies "in sync" (the drift is the bug).

## Tests (one per invariant; extend existing first)

Pinned old behaviour to **rewrite** (Change Policy Q4): `test_review_rounds_exhausted_fails_with_exit_5_blocked` (2942/3018), `test_review_with_no_verdict_fails_closed` (3052), `test_failed_report_read_fails_workflow_without_deadlock` (3147), `test_plan_report_with_blockers_fails_as_blocked` (3225), `test_child_failure_propagates_exit_code` (3343), and the invalid-contract case at 3061. They should assert `PauseForApproval("blocked N: …")` + `phase=Blocked`, not `Fail`.

New or extended (`cargo test --locked --lib pipeline::` / `engine::`):
1. `test_finding2_driver_unparseable_verdict_fails_closed` → extend: exit 6, fix the report, `--resume` → exit 0 clean; the journal holds 2 `child_started` for the review id (fails on old code: exit 6 again).
2. Build report `Outcome: BLOCKED` → exit 5; rewrite the report as done → `--resume` → reviewer spawned.
3. Rounds exhausted → blocked; plain `--resume` → still blocked, no new child; `--resume --rounds 3` → fix round 3 child started.
4. Same as 3 with a parent snapshot present (low `snapshot_interval`, or 20+ events): `--rounds` still honored.
5. Replay parity: after a blocked gate + resume, kill/re-run with and without a snapshot → same state and event seq (extend `test_finding6_resume_with_snapshot_vs_without_matches`).
6. Plan gate after an earlier blocked gate: `--resume` approves the plan (count-based `is_plan_gate`), and a blocked-gate resume is never taken as a plan approval.
7. Child watchdog exit 4 with no report → `--resume` waits on child journal `#2` (stub observer), not an instant exit 4; no second prompt is sent.
8. Gate approved=false → terminal `Failed` (workflow-level unit test).
9. `decide_build_gate` table: one test, cases {head==base+decl → NoChanges, head==base−decl → Blocked, head≠base+decl+always → Review, auto small → Skip, skip → Skip}.
10. Driver e2e: `--review always` + commits + `Outcome: no changes` → reviewer spawned (fails on old code: exit 0 clean). `head==base` + declaration → clean, with the pfile line.
11. `engine::runner`: two sequential `PauseForApproval`/`ApprovalResolved` cycles, kill between them → replay re-dispatches nothing (guards the per-count logic the design relies on).

## Risks

- **Restart archives an unedited report.** If the Lead resumes without touching the report, the mtime < `prompt_ts` archive (`mod.rs:1212-1218`) moves it away. The restart then waits and goes idle → exit 3. This is recoverable but noisy; the builder should verify the order relative to finding 6 (stale-report acceptance), which touches the same lines.
- **Journals written before this change stay terminal.** Pipelines that already hold `workflow_failed` stay dead. One-off: the Lead re-runs them fresh. No migration proposed.
- **The `blocked N:` prefix carries the exit code in a string.** Covered by the parse test. A typed field would need an engine contract change.

## Lessons

A recoverable stop in an event-sourced workflow is a pause/resume gate, never `Fail`; resume overrides must enter as journaled events, not as replay input — 2026-10-19, runs/truonglao-w2fail.md
