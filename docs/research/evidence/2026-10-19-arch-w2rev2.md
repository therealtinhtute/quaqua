## Findings

1. **High (correctness/recovery) — every engine `Fail` is an unrecoverable dead end for `--resume`.** `pipeline/mod.rs:861-869` converts `RunnerOutcome::Failed` to `finish(..., "blocked", code)` and leaves `state.finished = 0`, but the parent's `workflow_failed` event is terminal: `engine/runner.rs:342-356` returns `RunnerOutcome::Failed` on every later call before any state restore, and the resume call at `pipeline/mod.rs:829-839` reuses the same `pipeline:<task>` id. Failure: a reviewer writes `Verdict: not clean` (the now-correct fail-closed path, `mod.rs:2241-2248`) → exit 6; the Lead fixes the report and runs `quaqua pipeline --resume` → the runner replays the same `workflow_failed` and exits 6 again, forever. The same trap applies to an unfinished phase report (`mod.rs:2201-2207`, `2263-2268`), review-rounds exhaustion (`mod.rs:1949-1957`; this also makes the advertised `--resume --rounds N` a no-op), and invalid child output (`mod.rs:2087-2108`). The pre-cutover driver finished `blocked` without a terminal journal event, so resume re-read the phase (e.g. `origin/quaqua/arch-integ:crates/quaqua/src/pipeline/phases/review.rs` re-parsed the report after `--rounds` was raised). Evidence: code trace; `test_finding2_driver_unparseable_verdict_fails_closed` stops at the first blocked exit and never resumes; no test covers resume-after-`Fail`.

2. **Medium (correctness/gating) — `Outcome: no changes` skips review even when the branch has commits.** The engine's Build handler tests `report_has_outcome_no_changes` before the review gate at `mod.rs:2208-2216`, while the CLI only derives `skip_review` from the real gate (`mod.rs:1499-1605`); `report_has_outcome_no_changes` never checks that `HEAD == base_sha`. Failure: with `--review always`, the builder commits real work but writes `Outcome: no changes` (stale or contradictory report) → the CLI takes the `head != base` branch with `skip_review=false`, the engine still returns `Complete(clean)`, no reviewer is spawned, exit 0. The old `check_impl` applied the no-changes branch only under `head == state.base_sha` (`origin/quaqua/arch-integ:crates/quaqua/src/pipeline/phases/mod.rs:316-345`). The aa056d6 pfile line (`- build: no commits — builder declared 'Outcome: no changes'; nothing to review`) is also gone: the pfile now gets only `- status: clean` (`phases/mod.rs:74-76`).

3. **Low (correctness/fail-open) — the strict verdict parser still treats `clean` prefixes as 0 findings.** `mod.rs:2369-2376` returns `(0,false)` for any rest starting with `clean `, `clean,`, `clean:`, `clean -`. Failure: a reviewer writes `Verdict: clean, 3 findings remain` (or `clean - 2 findings below`) → `parse_report_content` yields 0 → `handle_review_verdict` (`mod.rs:1937-1945`) completes clean, exit 0, no fix round. `Verdict: not clean` and `Verdict: 0 of 3 findings addressed` are correctly rejected now, but this prefix window remains.

4. **Low (correctness) — a task slug containing the `review` segment hijacks the builder child as a reviewer.** `mod.rs:966` classifies by substring: `let is_reviewer = child_id.contains("-review-")`; the spawn branch at `mod.rs:984-1005` then spawns `state.reviewer` with `--review` under the builder's worker name. Failure: task `x-review-y` (allowed by the slug check at `mod.rs:507-512`) gives the plan child id `sude-x-review-y-plan`, which contains `-review-`; the pipeline never spawns the builder, creates a reviewer worktree named `sude-x-review-y`, and validates the plan report with `expect_verdict=true` (`mod.rs:1341`), so the plan is rejected as malformed → exit 6/blocked.

5. **Low (scope/audit evidence) — Challenge/Blockers are no longer copied into the pfile, and disputed is recorded as a blocker.** 48fcef2 removed the `log_challenge`/`log_blockers` calls from the plan/build/review/fix completions (`mod.rs:1435-1458`, `1665-1746`; the helpers remain exported at `mod.rs:19-22` but are unused). On a disputed outcome `mod.rs:854-859` passes `Some("disputed")` as the blocker, so `phases/mod.rs:78-80` writes `## Blockers\n- disputed` into `runs/pipeline-<task>.md`. Failure: after a challenge or an unfinished report, the pfile the Lead reads names no Challenge text and has a misleading Blockers line, contradicting the USAGE claim that "the pipeline stops blocked with the evidence copied in" (`mod.rs:52-56`); the evidence survives only in `runs/<builder>.plan.md|.build.md|.fixN.md`, which the unfinished path does not reference.

6. **Low (correctness/stale data) — a pre-existing runs file is accepted as the phase report on a fresh start or before the first prompt.** `mod.rs:612-617` checks only `pipeline-<task>.state`; `mod.rs:1212-1218` skips archiving while `prompt_ts == 0`; `mod.rs:1227-1243` then marks `already_delivered` from any valid `runs/<worker>.md`. Failure: start a task slug whose state file was removed but whose `runs/sude-<task>.md` remains → the plan child is completed with exit 0 without prompting the builder, and the pipeline pauses plan-ready on a stale plan. The old `wait_file` archived the report whenever `prompted == 0` (`origin/quaqua/arch-integ:crates/quaqua/src/pipeline/phases/mod.rs:184-186`). `test_finding2` itself pre-seeds the plan report and relies on this path.

7. **Low (correctness/residual #4) — the journal-loss seed path gives the fix prompt a bare filename and a stale findings count.** `mod.rs:202-232` sets `last_review_report = Some("<reviewer>-<task>r<N>.md")` (no runs-dir prefix) and copies `state.last_findings`; the new driver never assigns `state.last_findings` after the initializer (`grep`: only `mod.rs:642` and the seed read at `mod.rs:224`), so it is 0 there. Failure: after `runs/quaqua.db` is lost (the case the seed exists for), `--resume` at Fix tells the builder `reported 0 findings — full list in suhuynh-taskr1.md (readable)` (`mod.rs:1895-1907`); the builder's cwd is its worktree, so the relative name is not readable and the count is wrong. The normal path is fixed (`mod.rs:2133-2136` sets the real runs path).
