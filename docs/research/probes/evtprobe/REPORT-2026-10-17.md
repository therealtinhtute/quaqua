# herdr 0.9.5 events reliability probe — can events replace polling in quaqua watchdogs?

Read-only probe, 2026-10-17. Branch `quaqua/tieude-evtprobe`, script commit `8aca836`
(`docs/research/probes/evtprobe/probe.py`, analyzer `analyze.py`).

## Method (exact commands)

- Socket: `$HERDR_SOCKET_PATH` = `~/.config/herdr/herdr.sock`, newline-delimited JSON:
  request `{"id","method","params"}`, pushed events as `{"event","data"}` envelopes.
  Subscribe ack: `{"id":...,"result":{"type":"subscription_started"}}`.
- `docs/research/probes/evtprobe/probe.py <outdir>` holds ONE `events.subscribe` connection
  subscribing `pane.agent_status_changed` for every pane that exists at connect time,
  `pane.exited` for agent panes, and global `pane.agent_detected`; logs every received line with
  local receive ms (`events.jsonl`). In parallel it cross-checks `herdr agent get <name>` every
  10 s, `herdr agent list` every 1–2 s (`polls.jsonl`), and full `ps -axo pid,ppid,command`
  every 20–30 s (`ps.jsonl`).
- Runs: smoke 8 s @19:16:08; run1 780 s @19:16:33 (`EVT_DURATION=780 EVT_POLL_LIST=2`);
  run2 360 s @19:25:48 (`EVT_DURATION=360 EVT_POLL_LIST=1`, added the pane `wP:p14` that was
  created after run1 subscribed). Raw logs: `/private/var/folders/…/T/opencode/evtprobe-{smoke,run,run2}/`.
- Side-tests: wildcard subscribe `{"type":"pane.agent_status_changed"}` (no `pane_id`) →
  `invalid_request: missing field pane_id`; second `events.subscribe` on the same connection →
  silent EOF (no error frame, connection closed); subscribe to a stable pane → no initial
  snapshot (only the ack, then nothing until a real transition); 13-min connection saw zero
  keepalive frames; `events.wait` `timeout_ms:3000` → error `timeout` after 3.01 s;
  `herdr agent wait <n> --until idle --timeout 40000` → `timeout` after 40.14 s (so CLI waits
  and the raw primitive both honor timeouts; whether the CLI uses `events.wait` internally is
  not observable from outside — binary string says "agent.wait is handled by the api server").

  during the window; matches not requested).

  long turn); opencode coverage rests on the done transition (#6) + the fact that opencode
  statuses are pushed through the same `pane.report_agent` path as omp/claude (plugin sends
  `source:"herdr:opencode"`, omp `"herdr:omp"`).

## (2) Background shell: no false idle mid-turn; idle at turn end is a real risk

- Measured (mid-turn): my own session ran a background shell (`zsh -c sleep 150`, pid 36390,
  child of my opencode server pid 27954; observed alive in ps snapshots 19:16:53–19:19:03).
  My pane polls every 10 s remained `working` (seq 113) for the whole window, and **zero**
  status events were emitted for `w9:p3C`. A background shell does not by itself move an
  opencode agent out of `working`, and it does not hold a false idle *during* a turn.
- Mechanism (turn end): the installed opencode integration
  (`~/.config/opencode/plugins/herdr-agent-state.js`, v13) maps opencode events 1:1 —
  `session.idle → reportState("idle")`, `session.status` idle→idle / active|busy|pending|…→working,
  `tool.execute.*`→working, `permission.asked|question.asked|session.error`→blocked. An
  opencode background shell is not part of the session's busy state, so when a turn ends while
  the background shell still runs, opencode emits `session.idle` and herdr reports **idle**.
  An event-based watcher fires exactly the same false "idle" as polling — events remove polling
  latency, not this failure mode. (omp self-reports the same way via its extension, with a
  250 ms idle debounce.) Direct in-window observation of the turn-end case was not possible:
  I cannot end my own turn mid-task, and no other opencode agent ended a turn with a live
  background child in the window; this part is plugin-mechanism plus the measured mid-turn
  behaviour above, and should be treated accordingly.
- Operationally: keep the watchdog's run-file + progress guards regardless of events; do not
  wire any watcher action to "idle arrived" alone.

## (3) Latency: events land inside the poll bracket, ≤ ~1.6 s bound, typically hundreds of ms

For each of the 8 transitions, `event_ts` fell strictly between `poll_prev` and `poll_new`, so
the true transition→event latency is bounded by `event_ts - poll_prev` (upper) and
`event_ts - poll_new` (lower, negative = event arrived before the next poll could see it):

| # | agent (kind) | to | upper bound (ms) |
|---|---|---|---|
| 1 | sude-effwire (omp) | done | 400 |
| 2 | quaqua-rs-lead (claude) | working | 888 |
| 3 | quaqua-rs-lead (claude) | done | 1300 |
| 4 | quaqua-grid-lead (claude) | working | 1565 |
| 5 | quaqua-grid-lead (claude) | done | 449 |
| 6 | tieude-promptfix (opencode) | done | **294** |
| 7 | quaqua-grid-lead (claude) | working | 961 |
| 8 | quaqua-grid-lead (claude) | done | 161 |

No event needed a polling cycle to be noticed: 8/8 arrived (receipt timestamp) before the first
poll that could observe the new status, i.e. each event beat the poll that confirmed it. With
1 s brackets the tightest bounds are 161/294/400 ms; worst-case bound 1.57 s at 2 s polling.
Bound width = poll interval; the push path itself adds little (self-report → server → fan-out
round-trips the same socket CLI calls use).

## Verdicts

1. **Deliveries: yes, with a connect-time coverage contract.** All 8 observed transitions on
   subscribed panes arrived exactly once, in order, status-correct, incl. omp and opencode.
   0 missed, 0 wrong, 0 duplicates. But subscriptions are pane-pinned with no wildcard, no
   snapshot, one subscribe per connection — a watchdog must pin panes, read current state at
   connect, and reconnect+re-sync on topology change. `pane.exited`/`output_matched` unproven.
2. **Background shell: not a false idle mid-turn (measured working throughout, no event);
   at turn end herdr reports idle even while the shell runs (plugin mapping `session.idle→idle`)
   → an event-based watcher still fires the false idle, same as polling.** Watchdog guards must
   stay based on run files/progress, not idle alone.
3. **Latency: push wins.** Events arrived within (0, ~1.6 s] of the transition in all 8 cases,
   most within ≤500 ms; never after a poll could have seen it. `events.wait` (with honored
   `timeout_ms`) is the notify-once primitive; a subscriber + `agent list` re-sync replaces the
   10 s `agent get` loop with no transition loss in this window.

Residual risks: opencode idle/done sample = 1; `pane.exited`/`output_matched`, rapid
sub-poll transitions (possible coalescing) and long-idle connection keepalive are untested;
`herdr agent wait` internals not proven.

## Lessons

- herdr events are per-pane, not per-name: subscribing status requires `pane_id` per pane, new panes are only announced by `pane.agent_detected` — event watchers need a connect-time state read + reconnect-on-topology-change, or they silently lose panes — 2026-10-17, runs/tieude-evtprobe.md
- opencode/omp statuses are self-reported (`session.idle→idle` etc.), so "idle" at turn end with a live background shell is expected; watchers must never treat a status event as completion proof — 2026-10-17, runs/tieude-evtprobe.md
