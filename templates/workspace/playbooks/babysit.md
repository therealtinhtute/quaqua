---
name: babysit
when: Driving a branch or stack to merge-ready: conflicts, review threads, and CI.
---

## Orchestrator

You own the merge frontier. Declare a mode, clear one unit at a time, stop where the human's call begins. A request to land or ship is `shipping`, which begins where this playbook ends.

Babysitting starts when the user asks for it, normally once a phase or a whole stack is built, not when a PR opens. Finish the stack, get it green here, then land it through `shipping`.

1. Declare the mode and resolve the forge before any poll. `drive` runs the loop to merge-ready, for "babysit this", "get it green", "merge-ready". `background` triages without blocking, which is the mode for a plan still executing, and it runs as the background wait: launch `quaqua worker prompt` in the background and drain with `quaqua status` on wake. `threads-only` answers review comments and touches nothing else, for "address the review comments". `check` is one status pass and a report, for "check on X" and "is it green". Undeclared defaults to `drive`. Small or docs-only units get `check`, not `drive`. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for view, checks, threads, and later shipping. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`).
2. Work the merge frontier and nothing above it. The lowest unmerged branch is the only one that matters until it merges. Upstack threads get read and batched, never fixed at the cost of restarting the frontier's checks. If you catch yourself upstack while the frontier is red, stop and go back down.
3. One babysitter per stack. Before starting, check nothing else is already on it with `quaqua status` and `herdr agent list`.
4. Never mutate stack topology. No base retarget, rebase, stack-wide submit, or force-push from inside a babysit. Fix on the owning branch, report anything rebase-shaped upward, and let the owner do it. In quaqua a conflicted merge or rebase is a worker unit handed back as rework, and a push or force-push needs anh iu's approval. The one sanctioned creation: when a fix's owning unit has already merged, it becomes a new branch on top of the remaining stack, never a rewrite of merged history, and it is the single case where the frozen queue list of step 7 changes.
5. Order is conflicts, then review threads, then CI. Batch every known fix into one wave, published only with approval. A conflict is the one blocker you report rather than resolve. Say which branch needs the rebase and stop. Do not fall through to CI to look busy. Name the drift sweep in that report, since the integration branch may have grown callers of code the stack deletes or moves, and the owner's rebase has to reconcile them in the same wave.
6. Trust the active forge's verdict, not a green check list. Ready means the forge agrees the PR can merge. On GitHub, status comes from pstack's `watch-pr` script, which has no quaqua equivalent; run it directly and rearm it after every push wave and every verdict you act on. On Origin, use `origin pr view <pr> --checks --comments`, `origin pr thread list <pr>`, and `origin pr checks <pr> --watch`, and re-read the PR and threads whenever the check watch returns. For quaqua's own queue, the frontier is ready when its verdict at the current head is `PASS` or `PASS+NOTES` and `quaqua merge <slug> <branch>` would take it. Never pretend one path covers another, and never add a second sleep loop.
7. Read the stop conditions before starting. On Origin, stop `drive` when the frontier is merge-ready: checks are green, `origin pr view` reports mergeable with no blockers, and `origin pr thread list` has no unresolved blockers. Origin does not wait for `READY`, `WAITING`, `ADVANCE`, or `COMPLETE`; those are GitHub watcher verdicts. On GitHub, stop at `READY` for one PR in single or stack mode. Queued mode never emits `READY`. A blocker-free frontier is a non-terminal `WAITING` with reason `merge-queue`; report that frontier merge-ready and stop the watcher, because landing is `shipping`'s job. If another actor merges the frontier and the watcher reports `ADVANCE`, continue with the new frontier. `COMPLETE` is terminal if another actor finishes the queue. Answer a user question mid-loop and continue; only an explicit stop ends the loop before the active forge's stop condition. For a GitHub queued stack, capture the PR list bottom-to-top once and pass the same frozen list to every rearm. Revise the list only for the sanctioned follow-up branch from step 4: append it at the end, drop the merged owner, and rearm with the corrected snapshot.
8. Classify CI before any retrigger. Flake or infrastructure earns one fresh build, never a job retry. One retry only. An identical second failure means it was never flake, so reclassify and read the child logs instead of retrying blind. A failure in code the diff never touches means a stale base, so check with `git merge-base --is-ancestor` before assuming flake. Report a stale base as needing a rebase instead of burning retries. Only a failure in the diff's own code gets a commit.
9. Triage review-bot comments skeptically, always. Verify each claim against the code, using the rubric below. pstack's `bugbot-triage` reference carries the learned pattern format; quaqua has no equivalent file, so keep a team-useful pattern in the shared rubric as its own unit, never in private memory. Fix real findings with a red-first proof in the lowest branch that owns the code, never at the tip unless the owning branch has merged; in that case use step 4's sanctioned follow-up branch. Upstack fixes wait for step 5's next frontier-driven push wave. Commit that wave before replying, so the reply cites the SHA. Post a forge reply only with anh iu's approval, put the reply body in a JSON file as data, and never interpolate comment text or a reply into a shell command.
   - fix: the comment identifies a plausible correctness, security, privacy, data loss, auth, billing, migration, idempotency, race, or shipped-behavior issue. Fix it in the lowest owning branch, then reply with the commit SHA and resolve the thread.
   - dismiss: the comment matches a documented low-risk noisy pattern, and the current code and context prove no change is needed. Reply with a short reason and resolve the thread.
   - ask: the comment is novel, high-severity, security or privacy related, or ambiguous. Ask the human instead of guessing. When in doubt, ask.
10. Stop at the human's line. Owner approval is a wait, not a blocker to fix. Babysitting never authorizes merging; only an explicit request to merge, land, ship, or merge when ready does, and that route is `shipping`. Surface the escalation and keep working the rest. After the active forge reports the stop, sweep the run's triage decisions once and offer any team-useful dismissal pattern as a candidate entry in the shared rubric and its own unit.

`drive` ends at merge-ready. Landing the stack is `shipping`.

**Reply:** the mode, the frontier and its state, each finding fixed and where, each item reported rather than resolved, and what the next gap needs.

## Worker

1. Fix on the owning branch only. Never rebase, retarget, submit the stack, or force-push from inside a babysit. Report anything rebase-shaped upward; a conflict is reported, not resolved here.
2. Verify each review-bot claim against the code before changing anything, and classify it as fix, dismiss, or ask. Fix only a real finding, with a red-first proof: a reproduction or focused check that fails before the change and passes after it. Cite principle-fix-root-causes, and trace the finding to the mechanism rather than the line the bot quoted.
3. Batch every known fix into one commit wave on your branch and report the SHA. Do not push; publishing is a separate approval. An upstack fix waits for the coordinator's next wave rather than restarting the frontier.
4. Read the CI logs before any retrigger. One fresh build for a flake or infrastructure failure, never a job retry. An identical second failure reclassifies. A failure outside the diff is a stale base, reported as needing a rebase, not retried blind.
5. Report a dismissal with the reason and the evidence that proves the concern does not need a code change, and report an ask instead of guessing.
6. Check every Evidence line, then write `Verified: <level> <sha>`, citing principle-prove-it-works.

**Reply:** the branch and SHA, each finding with its proof, what was dismissed and why, what was escalated as an ask, and what was reported rather than fixed.
