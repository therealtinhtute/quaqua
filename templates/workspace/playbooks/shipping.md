## Orchestrator

You own what lands. Verify each unit independently, land only the verified run from the root, then keep your hands off the stack. Landing on main stays anh iu's approval, in every case.

1. Resolve the forge for any pull request that mirrors a unit. `gh` is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). In quaqua the unit of landing is a worker branch `quaqua/<name>` and the landing command is `quaqua merge <slug> <branch>...`; a pull request, when the project uses one, mirrors that branch.
2. Require one independent verdict per unit, at its current head, from an agent that did not write the code. Spawn the verifier as its own worker with `quaqua worker spawn --review --base quaqua/<unit> <name> <kind> <repo>`, on a kind whose `can_review` is true and whose harness differs from the builder's per `models.md`; a different kind alone is not enough, because two kinds can share one harness. `--base` is the only spawn input that cuts the verifier's worktree at a ref: without it the worktree starts at the repo HEAD, and a verifier that checks the unit out later moves that HEAD, which the baseline recorded at spawn rejects as a moved worktree. The verifier runs the change the way a user would on the matching surface at the head its worktree already holds, and reads the range from the parent point to that head — the merge base with the branch below it, or with `quaqua/<slug>-integ` at the bottom — without checking anything out. It records `Verdict: PASS`, `PASS+NOTES`, or `FAIL` in its report. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
3. Re-check that the verdicts still describe the code. A verdict covers a patch, and a rebase moves every unit above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. Land only the contiguous verified run rooted at the bottom, in order per principle-sequence-verifiable-units. Walk up from the lowest unmerged branch and stop at the first one without `PASS` or `PASS+NOTES`. The branches below it are the run, and the top one is the ceiling. A verified unit above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto the integration branch and land on its own, but it needs a fresh verdict first, because its old one ran with that code beneath it and the integration branch does not have it.
5. Land bottom-up, one branch at a time, by passing `quaqua merge <slug> <branch>...` only the contiguous verified list. Pass `--check '<project test command>'` (or set `QUAQUA_CHECK_CMD`) so every merge runs the project check; with neither set the command warns and merges without checks, so never land that way. It merges one branch at a time into `quaqua/<slug>-integ` and on a check failure or conflict undoes that merge and returns rework to the Peer (exit 2 or 4); when the integration base fails without the branch it exits 3 and holds the queue for the CoS. Read the integration branch back after each pass with `git -C <repo> log --oneline -1 quaqua/<slug>-integ` and compare it with the revision the merge printed, because that is the only record that the merge landed. On a PR-backed project a requested auto-merge is not a merge. Never push, never rewrite integration history, and never touch main; a main merge is a separate irreversible step that needs anh iu's explicit approval.
6. Leave the stack alone while it lands. Step 5's merge of the next branch is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. A base that moves when its parent lands is expected, not damage to repair. If a merge stalls, find out why before you change anything. For a GitHub-backed pull request the forge watcher is pstack's `watch-pr` script, which is GitHub-only and has no quaqua equivalent; on Origin use the check watch in `babysit` step 6. Run either outside quaqua and never add a second sleep loop.
7. Stop at the ceiling. Extending the run takes new verdicts, so it is a new pass through step 2. Pausing for the main-merge approval is the one place this playbook blocks, because that action is irreversible per principle-never-block-on-the-human.

**Reply:** the verified run and its ceiling, each unit's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.

## Worker

1. Take only the unit you were assigned, at branch `quaqua/<unit>`: your worktree was cut at that branch's head, so never check out or switch branches, because a moved HEAD voids the baseline recorded when your worktree was made. If you wrote any of its code, stop and say so in the report; the coordinator assigns another verifier. Your own build passing is not a verdict.
2. Resolve the forge the same way the Orchestrator does. `gh` is the default; use `origin pr` only when Origin resolves the repository. Record any fallback in the report.
3. Run the change the way a user would on the matching surface (CLI, TUI, API, or Web), at the head your worktree holds. Read the range from the parent point to that head — the merge base with the branch below it, or with `quaqua/<slug>-integ` at the bottom — with `git -C <worktree> diff <parent>..HEAD`, so verifying never moves HEAD. Capture the exact commands, the output, and any artifact. A green suite shows branch behavior, not that the change works as a user expects. Green CI and a bot approval are not evidence.
4. Report exactly one verdict and change nothing: `PASS` when the change works as a user would exercise it, `PASS+NOTES` when it works with notes a reader needs, `FAIL` with the failing observation and the surface it failed on. Record it as the report's `Verdict:` line. Never post outward; a PR comment or review is a publishing action that needs anh iu's approval.
5. Check every Evidence line, then write `Verified: <level> <sha>`, citing principle-prove-it-works.

**Reply:** the verdict, the surface and commands run, the SHA verified, the notes or failure you observed, and anything you could not exercise.
